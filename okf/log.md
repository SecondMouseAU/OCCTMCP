* **Update**: SecondMouseAU/OCCTMCP#277. `get_selection` passes a pick on a 2D drawing entity through instead of reporting "Body not found". `SelectionJSONEntry` decodes the optional `entity` (the DXF identity as one string, SwiftDXF's `Identity.id`, such as `8E/31`) and `entityType`, and `resolveSelection` routes `kind: "drawing-entity"` before the body lookup. The row is `bodyId` (the drawing case), `kind`, `entity` and `entityType`: no `selectionId`, `anchor`, `index` or `uid`, and nothing recorded in the selection registry. The decisions: a drawing-entity entry with no usable `entity` (missing, `null`, empty, blank or not a string) is that row's error, not a pass-through; a drawing-entity entry, or an entry of an unknown kind, may omit or mistype `index` and `uid`, and any entry may mistype `entity` or `entityType`, without making the file malformed (a model entry still decodes `index` and `uid` strictly); `get_selection`'s text does not escape slashes, so `8E/31` reads as written; model and drawing picks in one file keep their order and count; any other unknown kind is still a per-entry error, now checked before the body lookup so a kind for a body that is not in the scene reads as an unknown kind and not "Body not found"; `highlight_selection` is unchanged. `ResolvedSelection.index` is now optional. The Node server never reads `selection.json`, so it needed no change. Wire format settled in SecondMouseAU/OCCTSwiftInteraction#45 (ACADStudio D-124, Q-33).

## 2026-11-15

* **Update**: #271. The drawing read tools read through OCCTSwiftIO's `DrawingLoader` on SwiftDXF 0.4.0, now that OCCTSwiftIO 2.0.0-beta.6 compiles against it (OCCTSwiftIO#60). The SwiftDXF cap is gone. DXF, DWG (SwiftDWG, in process) and JWW (SwiftJWW) are read from their bytes. `expandBlocks` (default true) and `skipPaperSpace` are arguments of all four tools and are echoed under `source.options`, because the ids depend on them. Hatch and leader are entities with records and bounds; every entity and dimension carries its DXF `handle` and `locator` (and, once expanded, the `via` references and `blocks` it came through); a dimension reports its computed value, rotation, oblique angle and style, and a stored measurement of -1 or 0 is absent. An INSERT is no longer counted as skipped once SwiftDXF has expanded it (one that stays, for a block the file does not define, still is), the loader's warnings come through as data, and the format is told from the bytes, not the file extension. Not done: matching an entity by handle as an input (the id is still the index), measuring a hatch, and DWG's `CADFileFormat` case in OCCTSwiftIO.

## 2026-11-12

* **Update**: #257. `execute_script` writes into a stage directory, not the scene. The child gets `OCCTSWIFT_OUTPUT_DIR` pointing at a new directory under the system temp directory (the variable OCCTSwiftScripts 1.7.1-beta.4 reads; `OCCTMCP_OUTPUT_DIR` is no longer exported, and the harness never read it, so a host's `outputDirectory:` never reached the child before). The run is classified by exit code, the `run-failed.json` marker and the stage's manifest; only a clean run is promoted, and a failed one leaves the scene as it was. The default promotion replaces the scene (a script's manifest has always meant the scene as that script built it) under `ManifestStore.update`, copying listed files in under run-unique names first and removing the previous manifest's files after; `makeOCCTMCPServer(scriptStagePromoter:)` lets a host promote instead. `scriptsPin`, which was 1.4.2 and so resolved the stable 1.7.0 without any of this, is 1.7.1-beta.4 and a test holds it equal to `Package.swift`'s. Open question for the owner: whether `execute_script` should merge into a populated scene as `occtkit import` does; it replaces, as it always has.
* **Update**: #261. An `ExtraTool` handler can now add a body to the scene and find one again by id through the code the built-in tools use: `SceneBodies.add(shape:)` (the staged write, manifest lock, history snapshot and write observer that `read_brep` and `import_file` now share, with body ids checked to be usable as file names), `SceneBodies.body(withId:)` and `SceneBodies.shape(ofBody:)` (format dispatch and the host's shape provider). `OCCTMCPContext.reportProgress` sends MCP progress for a handler when the client asked for it. `ExtraToolSessionTests` pins the rest of the contract through a real client and server: state held by a handler survives between calls, calls run concurrently, the scene directory and a client's cancellation reach the handler's task (moving dispatch onto `Task.detached` fails these), and a server is released with its handlers' state once its session ends. A request the client cancelled now gets no response, as the MCP spec asks (`registerTools` rethrows the cancellation). An add refuses a file name another body already has (case-insensitively) rather than overwriting that body's file, which `read_brep` and `import_file` now also do, and pushes the scene it replaced onto the history only once its write has succeeded.
* **Update**: #260. Four read-only drawing tools, 79 to 83 tools: `read_drawing`, `list_drawing_entities`, `list_drawing_dimensions` and `measure_drawing`, built on OCCTSwiftIO's DXF import (`OCCTSwiftIO` becomes a direct product of `OCCTMCPCore`; it was already in the graph). They return coordinates and numbers, never images, and never touch the scene. Entity ids are `e<index>` and stable only for the same bytes, so every result carries the file's SHA-256; what the reader skips (block inserts, hatches, splines) is counted from the raw file and reported; distances are exact OCCT extrema over edges built from the entities. A dimension's `valueFromPoints` (aligned, radius and diameter) is the length between its own definition points, the value when the file stores none and a check when it does. DXF only: `DWGLoader` is merged upstream (OCCTSwiftIO#53) but unreleased and JWW has no entity model yet (OCCTSwiftIO#54), and both return an error saying so. Page: `docs/reference/drawing-read.md`.
* **Update**: #265. `execute_script` could hang forever after its child had exited: `runProcess` called `Process.waitUntilExit()` after awaiting the pipe drains, and with no termination handler that waits on the run loop of the launching thread, which the task may have left. `runProcess` now waits on `ProcessExit`, built on `Process.terminationHandler`. Added the rule to `CLAUDE.md` Invariants and `Tools/ProcessExit.swift` to the `swift-server.md` catalogue.

## 2026-10-15

* **Update**: #250. `ManifestStore.update(willWrite:_:)`: advisory `flock` on `manifest.lock`, a callback that receives the exact bytes under the lock before the atomic rename, and every mutating tool moved onto it (re-applying its change to the manifest read under the lock). `write` takes the same lock. A malformed manifest is `ManifestError.malformed` everywhere, not "No scene loaded", and `read_brep`, `import_file` and `segment_mesh_zones` no longer overwrite it. Source-compatible: `ManifestStore.init(path:)` gained a defaulted `lockTimeout`.
