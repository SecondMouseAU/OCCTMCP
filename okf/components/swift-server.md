# The Swift server, file by file

`Sources/OCCTMCPCore/` (library) + `Sources/OCCTMCPServer/` (executable that connects stdio).

- `Server.swift`: `createServer()` factory: registers all 79 tools with their JSON Schemas, returns an `MCP.Server` ready to bind to a transport. Tests import `createServer()` to introspect the registry without binding stdio. The `get_api_reference` tool's `mcp_tools` category dumps the live registry as JSON Schema for LLM auto-discovery.
- `Tools/`: one file per tool family:
  - `ExtraTool` (in `Server.swift`, #196): a public `Tool` + `@Sendable` async throwing handler that an embedding host passes to `makeOCCTMCPServer(extraTools:)` (default `[]`, so no behaviour change). `catalogTools(extraTools:)` lists built-ins then extras; `dispatch(callName:arguments:extraTools:)` checks extras first. A name collision with a built-in is won by the extra (the built-in leaves the catalog, no duplicate names); among extras the last wins. A thrown handler error becomes an `isError` result. `get_api_reference` `mcp_tools` dumps the catalog including extras (dispatch threads `extraTools` to it). Docs: `docs/reference/core.md`
  - `CoreTools.swift`: `get_scene`, `get_script`, `export_model`, `get_api_reference`
  - `ExecuteScriptTool.swift`: `execute_script` (writes Swift to tempfile, `occtkit run` via the resolved binary, parses manifest)
  - `SceneTools.swift`: `remove_body`, `clear_scene`, `rename_body`, `set_appearance`, `compare_versions`, `export_scene` (pure manifest manipulation; `export_scene` runs a templated script via occtkit)
  - `IntrospectionTools.swift`: `validate_geometry`, `compute_metrics`, `query_topology`, `measure_distance` (in-process via OCCTSwift). #119: `query_topology`'s edge results carry `endpoints` (every edge kind) plus a unit `direction` for LINE edges, and `circleCenter`/`radius`/`axis`/`startAngle`/`endAngle` for CIRCULAR edges, via the shared `SelectionTools.edgeGeometryFields(edge:)` helper (also backs `select_topology`'s edge anchors, so both tools agree on the same fields)
  - `FaceAdjacency.swift` / `OppositeFaces.swift` (#199, #201): `query_topology`'s face-only `includeNeighbors` / `oppositeFaces`. `FaceAdjacency.faceAdjacency(shape:)` is the ONE place AAG adjacency is read: AAG nodes are `orientedFaces()` occurrences (OCCTSwift#642), so every edge is mapped through `AAGNode.distinctFaceIndex` into `faces()` space (matching `face[N]` and `get_selection`'s `index`), occurrences of a shared face merge (`sharedEdgeCount` sums, duplicates collapse, self-edges drop) and `faceCount` is `shape.faces().count`. `graph_select` `face-neighbors`/`face-adjacency` and `graph_ml`'s `faceAdjacency` block are built on it (#201: they used to emit raw occurrence indices, and bounds-checked against `aag.nodes.count`, which exceeds `faces().count` on a shared-face compound). `OppositeFaces.Finder` hints the nearest anti-parallel planar face behind a face whose projection overlaps it. `exact` traces both faces' outer wires (`Wire.allEdgePolylines`, chained into one loop) and runs `PolygonOverlap`, a positive-area overlap test (proper edge crossings, strictly-interior vertices, and inward-offset edge probes for coincident boundaries) so a face that only touches the range or sits in an L's missing corner is rejected; holes are ignored. A face whose wire does not chain falls back to the bbox test per pair, reported as `oppositeFace.method: "bbox"` plus a `warnings` entry, never silently. Advisory only: non-planar faces get none. The 200-face guard (`maxUnlimitedFaces`) applies to the matching face count when no `limit` is given, since opposites are O(faces) per face
  - `VertexFitTools.swift`: `measure_vertex_fit` (#118): exact per-vertex distance table from `fromBodyId`'s own vertices to `toBodyId`'s real BRep geometry, the vertex-fit instrument neither `measure_distance` (body-to-body, capped at 32 pairs), `measure_deviation` (mesh-to-mesh, approximate, no raw per-vertex table), nor `find_correspondences` (only matches `toBodyId`'s topological vertices, a handful on a typical solid) provides. Every scene body is stored as BRep (an STL import is a facet shell, one planar face per triangle, per `import_file`), so `fromBodyId`'s own `Shape.vertices()` ARE its mesh corner points; no re-meshing needed. Confirmed empirically (`VertexFitToolsTests.realSTLImportVertexCount`, a real STL import, not a primitive box), not just assumed: `import_file`'s STL path sews/heals on import, so `Shape.vertices()` returns the true deduped corners, no separate dedup pass needed here. Requires `fromBodyId != toBodyId` (every vertex would trivially read ~0 otherwise). Per vertex: `Shape.vertex(at:)` builds a single-point Shape, `.distance(to:)` gets the exact BRepExtrema distance, `.distanceSolutionDetail(to:solutionIndex:0)` classifies the nearest entity kind (vertex/edge/face) via `supportType2`. Entity INDEX isn't resolved (only a parametric location on the entity is available; reverse-matching that against every candidate face/edge per vertex would multiply the already-per-vertex cost by the target's face/edge count for a documented "nice to have"). **TWO PASSES, not one**: `.distance(to:)` and `.distanceSolutionDetail(to:solutionIndex:)` each independently construct their own `BRepExtrema_DistShapeShape` (checked against the OCCTBridge source, neither reuses the other's computation), so pass 1 computes `distance` alone for every sampled vertex and pass 2 spends the second, expensive `distanceSolutionDetail` call ONLY on entries that end up in the response (worst-N by default, or every entry when `includeAllVertices: true`) rather than every sampled vertex. Response is mean/rms/max/p95 plus a worst-N table (largest-first, default 20, stride-subsampled against `maxVertices`); `includeAllVertices: true` for the full per-vertex table
  - `DeviationTools.swift`: `measure_deviation` (meshes both bodies, KD-tree → exact point-to-triangle distance both directions. As of #62 the report is a *vector*: max / rms / mean / p95 / `signedMean` (+ proud / − shy) / signedMin/Max, plus an optional per-section signedMean sweep when `sectionAxis`+`sections` is given. Also the shared signed-distance engine (`TriMesh`, `signedQuery`, `signedDistances`, `closestPointOnTriangle`) reused by every other signed diagnostic. The certify-a-reconstruction metric `measure_distance` can't give since it's min-only; #41/#62). **`SignMode` (#72)**: the sign comes from whichever reference triangle a sample is judged against, and taking the *nearest* one breaks against an open thin-walled reference: a flank 4.5 inside a 2 wall is only 2.5 from the wall's inner surface, which therefore wins and (facing the cavity) reports +2.5 proud for a 4.5-shy part, confidently and untied, so #74's coin-flip guard never fires. Default `.robust` gates the correspondence on normal agreement (`signedQuery` takes the sample's OWN outward normal, `TriMesh.vertexNormal` for vertex samples, the winding normal for the heatmap's per-triangle centroids, and rejects reference triangles whose normal opposes it); if the whole k-neighbourhood is the far wall it widens once to `widenedK`, and if no compatible surface is in reach the sample is flagged `ambiguous`. `.nearest` restores pre-1.17 behaviour. **`SignedHit` carries two distances and they must not be conflated**: `nearest` (closest surface, full stop) backs the unsigned figures (max/rms/mean/p95/worstPoint/symmetricHausdorff/maxAbs/withinTolerance) so `signMode` never moves them; they mean in 1.17 what they meant before; `signed` backs the sign channel (signedMean/Min/Max, `sectionize`, buckets, heatmap colour) and is the distance to the CORRESPONDING surface, so `abs(signed) ≥ nearest` under `.robust`. `max: 2.5` beside `signedMin: −4.5` is correct and diagnostic, not a bug. Signed aggregates use sign-reliable samples only and are **nil** when none are (zero would read as "perfectly centred"); `sectionize` still takes its axis span from ALL samples so `offset` doesn't re-base. `ambiguousFraction` ≈ 1.0 ⇒ the reference's winding is likely inverted relative to the sampled body. Sizing gotcha: these meshes are unshared triangle soups (3 verts per triangle, no sharing: 576 tris ⇒ 1728 verts), so `widenedK` must be several × what a shared-index mesh would need; 256 was silently too small and greyed out the very case the gate exists to fix. **`DeviationTools.standardMeshParameters(deflection:)` (#125)** is the canonical construction path for the shared `deflection`+`internalVertices`+`inParallel`+`allowQualityDecrease` mesh recipe every deflection-sensitive diagnostic tool uses (`TriMesh.init` itself included), a new tool should call it, not hand-roll another copy
  - `DeviationHistogramTool.swift`: `deviation_histogram` (#62): signed point-to-surface distribution (μ/σ/median/p95/extremes, percent-within-±tol, buckets) + optional histogram PNG. Takes `signMode` (#72); the distribution and its buckets are built from sign-reliable samples only: a flipped sign plants a mirror hump at −d and reads as exactly the bimodal systematic error this tool exists to spot, while magnitude-only figures (p95 / maxAbs / withinTolerance) keep every sample
  - `CrossSectionCompareTool.swift`: `cross_section_compare` (#61): slices BOTH bodies (meshed) with the SAME `OCCTSwiftMesh.Mesh.crossSection` `CutPlane` at N stations along a shared axis (identical (u,v) basis ⇒ directly comparable 2D profiles), per-section signedMean/RMS/area-ratio/centroid-offset + a pose-robust radial-signature shape scalar, with overlay PNGs. The detector for a systematic wrong-section. Stations span the two bodies' shared axis-extent overlap (reported as `overlap`); a section may be a closed contour OR an open polyline, so an open-shell reference (raw scan / STL skin) whose sections are open arcs still produces a comparison instead of reading as un-sliced: #66 (the fix falls back to the longest open path, flags open-profile stations, and warns on stations that sliced only one body). #70 (v2): default `outerEnvelope` mode compares the candidate against the reference's OUTER boundary per angular sector (radial max about the reference centroid, gap-filled across openings) so inner window-return / frame paths of a thin-wall / scanned part stop polluting the aggregate; `outerEnvelope:false` restores raw point-to-main-loop. Each station also reports `axisCoord` (world position along the axis, not just overlap-relative `offset`), and `envelopeShapeL2` gives a shape scalar that's defined for open profiles too. **#123:** the default `outerEnvelope` mode's per-station `rms`/`maxAbs` used to feed `envelopeDeviation` the RAW union of every contour a station's cut produced (outer boundary AND any inner window-return / bore loop), trusting the envelope's own per-bin max-radius selection to drop the inner ones; that only holds when tessellation is dense enough that the outer loop has a point in nearly every angular bin, which a real mesh cross-section (an axle bore running through a hub/rim profile, at typical deflection) is not, so a bin the outer loop skipped but the bore loop happened to land in read back at the BORE's radius and got treated as real data rather than a gap to interpolate across, reporting the bore-to-hub / bore-to-OD radius gap (100x-200x too large, insensitive to the station's real fit) instead of genuine profile deviation. Fixed by filtering to depth-0 (outer) contours before building the envelope's input points (`ProfileMath.outerEnvelopePoints`), reproduced exactly (maxAbs landing within 0.03mm of the reported bug's ~5.99mm plateau) by a rotated-but-geometrically-identical bored-tube regression fixture in `SignedSpatialDeviationTests`
  - `SymmetricDifferenceTools.swift`: `symmetric_difference_volume` (#122): the two ONE-SIDED volumes between `fromBodyId` and `referenceBodyId` (excess-only, missing-only) and their sum, the direct geometric fidelity figure a mean/RMS surface deviation can hide via cancellation. `boolean_op` cannot produce a true symmetric-difference solid against a mesh-only, possibly non-watertight reference (empirically, on a real STL: `subtract(solid, mesh)` fails, `subtract(mesh, solid)` fails); this instead classifies deterministic Halton-sequence sample points (default 300, `maxSamples`) against BOTH bodies' `OCCTSwiftMesh.Mesh.windingNumber(at:)` (>=1.7.0, no spatial acceleration: O(triangleCount) per call, hence the much smaller default than `measure_deviation`'s surface-sample tools). Classification is deliberately orientation-agnostic: `windingNumber` is exactly linear in triangle orientation (an inverted-winding mesh reads ≈−1 inside, not ≈+1), so a point classifies as inside when the value sits close to ANY nonzero integer (`round(w) != 0`), not specifically +1, since otherwise an inverted or nested-shell reference would silently report as missing its entire volume. Values near the 0.5 midpoint between integers are `ambiguous` (excluded from the volume buckets, reported as `ambiguousFraction`; `reliable: false` above 15%), the open-shell / self-intersection symptom this tool exists to stay robust against. Reports `symmetricDifferenceFraction` (1 minus IoU against the sampled union), a Monte Carlo `estimatedStdErrMm3` (a measured difference under ~2x this is noise, not necessarily a well-registered pair), and the exact BREP mass-properties volume as a cross-check where computable (silently unreliable for a non-closed shape, which is exactly the reference-body case motivating this tool)
  - `HeatmapTools.swift`: `signed_deviation_heatmap` + `overlay_render` (#63): the heatmap colours per-triangle signed distance via the diverging colormap by grouping a band's triangles into one flat-coloured `ViewportBody` (OffscreenRenderer has no per-triangle/per-vertex *surface* colour pass; only the point pass reads `vertexColors`), then composites a colorbar legend; `overlay_render` draws the reference mesh translucent (OffscreenRenderer's transparent pass: effective opacity < 1) over the opaque solid. #72 (two parts): #74 made `signedQuery` return `ambiguous` when a comparably-close candidate triangle disagrees on side, and the heatmap renders those grey instead of red/blue, excluded from `signedMin`/`signedMax`/`signedMean` and reported as `ambiguousTriangles`/`ambiguousFraction`. That covers genuine ties but NOT the reported case: an inner wall winning by a clear margin ties with nothing, so it stayed red. The v1.17.0 half adds the `signMode` correspondence gate in `DeviationTools` (see above); the heatmap passes each triangle's winding normal as the sample normal and grey now also means "no compatible reference surface in reach". A mostly-grey render ⇒ trust the magnitude or `cross_section_compare`, not the sign. Its per-triangle flat-coloured `ViewportBody.directMesh` band-group trick is what `MeshZoneTools`/`ZoneSweepTool` (#101/#102) reuse for per-zone and per-verdict colouring
  - `MeshZoneTools.swift`: `segment_mesh_zones` (#101): the MCP surface over `OCCTSwiftMesh.Mesh.segmented(_:)` (dihedral region-growing + primitive-fit merge, OCCTSwiftMesh#16/#17). Meshes the body (`DeviationTools.standardMeshParameters(deflection:)`, the same recipe as `DeviationTools.TriMesh`), segments, mints `zone:<bodyId>#<n>` (largest-first, matching `SegmentedMesh.regions`' own order) into `ZoneRegistry`, and reports per-zone `{triangleCount, areaMm2, areaFraction, bbox, meanNormal, boundaryLoops, adjacentZones, fit, slippage?}`. `adjacentZones` needs a WELDED mesh to see real triangle adjacency, but the only public weld entry point (`Mesh.welded(tolerance:)`) can silently drop degenerate triangles, which would shift triangle indices relative to the unwelded `MeshRegion.triangleIndices` this tool's own `triangleIndices` are indexed against; guarded by a post-weld triangle-COUNT check (proof nothing was dropped) with an honest empty-array + warning fallback rather than risking mis-attribution. Optional per-zone categorical PNG render (band-group trick, see `HeatmapTools`) and optional capped sub-body registration (`registerZones`/`registerCap`): each zone's `subMesh` round-trips through a temp STL (`MeshTools.writeMesh`) → `Shape.loadSTL` → `Exporter.writeBREP(allowInvalid: true)` as `<bodyId>_zone<n>`, mirroring `boolean_op`'s manifest-append pattern. **#109 (Phase 3): `slippage`**, per-zone `Mesh.slippage(forTriangles:maxSamples:)` (Gelfand-Guibas local slippage analysis, OCCTSwiftMesh#26/#31, >=1.6.0), reusing the EXACT SAME welded mesh + triangle-count-survival guard `adjacentZones` already established (the same correspondence problem: the classifier's `vertexNormals()` is only meaningful on a genuinely welded mesh, and the guarded weld's index correspondence is what makes `region.triangleIndices` valid against it); omitted (nil) per zone alongside `adjacentZones`, with its own warning in the same wording family, when the guard fails. Response field mirrors `SlippageResult` minus `eigenRatios` (an internal diagnostic, not bounded LLM output): `{kind, axisPoint?, axisDirection?, pitchPerRadianMm?, confidence}`. `axisDirection`'s sign is arbitrary (inherent to the eigenvector recovery) and its meaning is kind-dependent, the surface NORMAL for plane (never a sweep axis), the rotation/screw axis for cylinder/revolution/helix, the extrude direction for extrusion, `nil` for sphere/freeform; `confidence` is a spectral-gap diagnostic, not a probability, and reads low (not confidently wrong) for a near-symmetric body whose true eigen-spectrum has no clean separation to begin with
  - `ZoneSweepTool.swift`: `zone_continuity_sweep` (#102): a zone's (or whole body's) loftable-extent map. Resolves the zone's triangles from `ZoneRegistry` (re-meshing at the zone's OWN stored `params.deflection`, never a caller-supplied one, since `triangleIndices` only lines up with a mesh built at that exact deflection; a `MeshSignature` mismatch errors asking the caller to re-run `segment_mesh_zones`) or the whole body, `subMesh`s, then slices along an axis with the same `Mesh.crossSection`/`ProfileMath` machinery `cross_section_compare` uses. **Axis resolution (#109 adds the middle rung): `selectSweepAxis(record:explicit:)`**, a pure, geometry-free function (`ZoneSweepMathTests` covers it directly) resolving `axisSource` in priority order: `"explicit"` (the caller's `axis` argument, unconditional) > `"slippage"` (a `zoneId`-scoped sweep whose stored `ZoneRecord.slippage.kind` is in `{cylinder, extrusion, revolution, helix}`, NEVER plane, whose slippage axis is the surface NORMAL, sweeping along which is exactly wrong, and never sphere/freeform, which have none, with `axisDirection` non-nil AND `confidence >= 0.25`; below that floor, falls back to PCA with a warning naming the rejected kind/confidence) > `"pca"` (`principalAxis`: power iteration on the covariance, ~50 steps, no Accelerate dep, every whole-body sweep, since there's no zone-scoped slippage to consult, plus any zone-scoped sweep that didn't qualify for the slippage rung). Per-station signals (`lateralOffsetMm`/`profileRmsMm`/`profileMaxMm`/`arcLengthDeltaMm`) come from `ProfileMath.profileDelta`, reference-relative not absolute. The change-point pass (`detectRunsAndDeviations`) is a pure function over station indices + an injected `signals(reference:candidate:)` closure, deliberately factored out of any geometry so it's unit-testable on synthetic arrays, that greedily builds maximal within-tolerance runs (the "constant"/loftable extents) and the deviation intervals between them, each keeping the SAME frozen reference throughout (a run's own first station), only resetting when signals return within tolerance. Per the mandatory-analytic-verification policy this aggregation logic is independent of OCCTReconstruct's own engine, written from OCCTSwiftMesh primitives only. Render colours by nearest-station verdict (constant=blue/deviating=red/missed=grey, same band-group trick); optional per-station `profileRmsMm`-vs-`axisCoord` strip chart. Revolve-aware angular stationing for `revolution`-classified zones (stations about the axis rather than along it) is the #109 follow-up remainder, not yet implemented
  - `ProfileMath.swift`: 2D cross-section profile helpers (`mainProfile`/`mainLoop`, `Profile.usable`, `outerEnvelope`+`fillGapsCircular`+`envelopeDeviation`, `radialSignature`/`radialShapeL2`, `envelopeShapeL2`, `resampleClosed`), extracted verbatim (zero behaviour change; `CrossSectionCompareTool`'s own tests pass unchanged) from `CrossSectionCompareTool`, which now calls through to this file. Shared with `ZoneSweepTool` (#102), which adds `resampleOpen` + `profileDelta` here (unused by `CrossSectionCompareTool`): a reference-relative, real-mm (not the normalized shape scalars above) comparison for the OFTEN-open profiles a single zone's own slice produces. `profileDelta` is reversal-invariant for open profiles: `Mesh.crossSection`'s open-path point order isn't a canonical property of the surface, so two independent cuts of the SAME wall at different stations can come back walked in opposite directions; naive positional correspondence read that as a large (bogus) shape difference until this was caught by the #102 integration test and fixed by comparing both point orders and keeping the lower-RMS one. Known limitation (documented, not yet fixed): CLOSED rings don't get the same treatment: they're resampled from `loop[0]`, which is equally non-canonical, so two stations of a tube-like body can come back rotated and read as phantom `profileRmsMm`; the eventual fix is a best circular shift over the resampled points, and until then prefer zone-scoped (open-profile) sweeps over whole-body closed-ring sweeps for thin-wall bodies. `outerEnvelopePoints(contours:open:)` (#123): the depth-0-only point filter `CrossSectionCompareTool`'s outer-envelope mode now feeds `envelopeDeviation`, replacing a raw all-contours union that relied on `envelopeDeviation`'s own per-bin max-radius selection to drop inner (bore / window-return) loops, a reliance that silently broke under sparse (real-world) tessellation; see the `CrossSectionCompareTool.swift` bullet above for the failure mode
  - `ChartRenderer.swift`: pure-Swift Core Graphics + Core Text PNG helper (histogram, 2D profile overlay, colorbar legend, `categoricalPalette`/`overlayZoneLegend`/`stripChart` for #101/#102) and the shared diverging colormap. Headless; no Python/matplotlib, no AppKit
  - `MeshDiagnoseTools.swift`: `mesh_diagnose` (Phase 2 of the mesh-analysis expansion, `.claude/plans/2026-07-21-mesh-analysis-expansion.md`): a printability-check-list integrity report over `OCCTSwiftMesh.Mesh.integrityReport(weldTolerance:)` (1.3.0), watertight, edge/vertex-manifold, orientable, connected components (largest-first, capped 16 with a warning past that), boundary loops, Euler characteristic / genus, duplicate/degenerate triangle counts, sliver signals (`minAngleDegrees`/`aspectRatio`). `checks[]` (`buildChecks`, a pure function over the raw `MeshIntegrityReport`) derives pass/warn/fail verdicts: watertight/non-manifold-edges/non-manifold-vertices fail on any count > 0; orientable is reported `warn`/"not evaluated" rather than a verdict when non-manifold edges are present (the metric isn't meaningful there); single-component/degenerate/duplicate/slivers warn. Self-intersection is explicitly NOT checked (an `integrityReport` limitation, not this tool's), a self-intersecting closed manifold still reports `isWatertight: true`; documented in the tool description, the docs page, and here. Also un-stubs `MeshTools.computeQuality`'s `nonManifoldEdges` (previously hardcoded 0) by delegating to this same `integrityReport(weldTolerance:)` call
  - `MeshThicknessTools.swift`: `mesh_thickness`: the mesh-domain complement to the BREP-only `check_thickness`, which degrades on facet shells. Ray method (normal-opposite, first-hit): builds a `TriBVH` (see below) over `DeviationTools.TriMesh`'s triangles, stride-subsamples vertices (mirrors `directedStats`' `maxSamples` convention), and for each sample casts from `p - 1e-4·n` along `-n` (n = `TriMesh.vertexNormal`); first hit = local thickness. Rays that exit without hitting (open shells, or a zero vertex normal at a rim) are excluded from the stats and counted in `noHitSamples`. Optional `coneAngleDegrees` casts a deterministic fixed 5-ray pattern (centre + 4 at the cone boundary, NOT randomized jitter) and takes the MEDIAN hit (the SDF convention), more robust near edges/features than a single ray. `thresholdMm` adds a `belowThreshold` section (count/fraction/worst-8 points, fraction is of MEASURED samples, not of `samples` including misses). A hand-built hollow-box STL fixture (`MeshThicknessToolsTests`) pins a real characteristic of the single-ray method: a sample near a face's own outer edge legitimately overshoots a thinner opposing wall's smaller footprint and reads through to the FAR wall instead, not a bug, and why the fixture subdivides each face into a grid (so edge/corner samples are a bounded minority) and the test asserts median/p05, not min/max
  - `SymmetryTools.swift`: `detect_symmetry`: PCA candidate mirror planes verified with the existing `DeviationTools` signed-distance engine (pure MCP-side composition; rotational/axis symmetry is deferred). Centroid + all 3 principal axes via `symmetricEigen3x3`, a small from-scratch cyclic-Jacobi eigensolver for a symmetric 3x3 (this tool is the first caller needing all three axes, `ZoneSweepTool.principalAxis`'s power iteration only gives the dominant one). The covariance MUST use the exact per-triangle second-moment formula (`area/12·(9·m⊗m + A⊗A + B⊗B + C⊗C)`, a standard closed form, e.g. Gottschalk/Lin/Manocha "OBBTree" 1996) rather than treating each triangle as a point mass at its own centroid: on a coarsely-tessellated mesh (a box face split into just 2 large diagonal-cut triangles) the point-mass shortcut produces spurious non-zero cross-covariance terms large enough to rotate the "principal axes" well off a box's real, exact coordinate-aligned symmetry planes, caught by `SymmetryToolsTests`' box fixture. `symmetricEigen3x3` itself has a matching gotcha: the rotation-angle formula (`theta = (aqq-app)/(2·apq)` → `t` → `c,s`, the numerically-stable Numerical-Recipes form) must pair with the SAME sign placement of `s` in the Givens matrix (`g[p][q] = +s, g[q][p] = -s`) that its `A' = GᵀAG` zero-condition was derived for; the other placement needs the opposite-sign angle formula, and pairing them wrong doesn't error, it makes the target off-diagonal term GROW (verified doubling every sweep) instead of shrinking to zero, caught by the same box fixture. For each candidate plane (through the centroid, normal to a principal axis): reflects stride-subsampled vertices across it, measures each reflected point's UNSIGNED nearest distance back to the mesh's own surface via `DeviationTools.signedQuery(..., signMode: .nearest)` (`.nearest` mode never engages the #72 normal-compatibility gate, so its `.nearest` field is always the honest closest-surface distance). `symmetric` iff p95 residual ≤ `toleranceMm`; candidates sorted best-first, `bestPlane` set when any passes
  - `AlignTools.swift`: `align_bodies` (#104, closes the Phase 2 mesh-analysis expansion's 4th tool; was blocked on SecondMouseAU/OCCTSwiftMesh#22 until v1.5.0's `Mesh.aligned(to:options:)`, point-to-plane ICP with PCA pre-align + normal-space sampling + trimmed correspondence, Chen & Medioni / Rusinkiewicz & Levoy / Low). A thin GOM-style wrapper: `mode: "bestFit"` (default) runs the full upstream pipeline; `mode: "preAlign"` forces `maxIterations: 0` (the PCA/bbox coarse tier only, ICP refinement skipped); `localBestFit`/3-2-1/RPS-datum modes are deferred. Both bodies meshed at the SAME deflection (source-derived unless overridden) via `DeviationTools.standardMeshParameters(deflection:)`, the recipe shared with `DeviationTools`/`MeshDiagnoseTools`. The response's `transform` is 4x4 ROW-MAJOR (`transform[i][j]`, point mapped as `transform · [x,y,z,1]`), the OPPOSITE convention from the upstream `simd_double4x4`, which is column-major; `AlignTools.rowMajor(_:)` converts carefully (`rows[i][j] = m.columns[j][i]`, since `simd_mul(m,v)` computes "row i dot v" under that reading). `rotationAxis`/`rotationAngleDegrees` is an axis-angle decomposition of the 3x3 rotation block (`AlignTools.axisAngle(fromRotationRows:)`) with EXPLICIT guards for the two cases the general formula can't handle: identity (angle ~ 0, axis arbitrary) and a 180° rotation (the antisymmetric term the general formula divides by vanishes there; falls back to the symmetric part `S = (R+I)/2 = axis⊗axis`, pivoting on whichever diagonal of `S` is largest). Warnings surface the two upstream-documented limitations rather than silently trusting the transform: `converged == false` (bestFit mode only, preAlign's `converged` is always false by construction, not a signal, so that warning is suppressed there) and `residualRmsMm` exceeding 2% of the source body's bbox diagonal. `apply: true` mirrors `ConstructionTools.transformBody`'s in-place path exactly (`SceneHistory` snapshot, `HistoryRegistry.commit(ref: nil)` generation reset, no `*WithFullHistory` variant exists for an arbitrary caller-supplied matrix, only the named translate/rotate/scale/mirror/pattern primitives) via `Shape.transformed(matrix:)`, OCCTSwift's one general-affine (rotation+translation) primitive (`BRepBuilderAPI_Transform`/`gp_Trsf`). - `ZoneRegistry.swift`: actor-backed store of `zoneId → ZoneRecord` (#101), mirroring `SelectionRegistry`'s actor-cache shape plus `Annotations.swift`'s disk-sidecar persistence (`<output_dir>/zones.json`) one level up: zones are meant to survive a process restart so a later `zone_continuity_sweep` call can resolve one minted earlier, unlike `SelectionRegistry`'s deliberately ephemeral picks. `zoneId` format `zone:<bodyId>#<n>`, minted largest-first matching `SegmentedMesh.regions`' own order. Every mutation (`recordBatch`/`clear`) writes through to the sidecar immediately, so a fresh actor instance only ever needs to catch up from disk once (`loadSidecarIfNeeded`, gated on a one-shot flag), its very first touch of a given output dir. Each `ZoneRecord` carries the `SegmentParamsUsed` (including the exact `deflection`) and a cheap `MeshSignature` (triangle count + bbox) so `zone_continuity_sweep` can detect a stale zone (the body changed since segmentation) and error out telling the caller to re-run `segment_mesh_zones`, rather than resolving `triangleIndices` against the wrong mesh. **#109: `ZoneRecord.slippage: ZoneSlippage?`**, OPTIONAL (default `nil`) specifically so a `zones.json` sidecar written before #109 (no `slippage` key at all) still decodes: Swift's synthesized `Decodable` treats a missing key on an `Optional` stored property as `nil`, not a decode error, so no sidecar version bump was needed (a dedicated old-format-sidecar test in `SlippageIntegrationTests` proves this end to end, including that `zone_continuity_sweep` falls back to PCA cleanly). `ZoneSlippage` mirrors `SlippageResult` (SIMD-free: `[Double]?` arrays) minus `eigenRatios`.
- `HistoryRegistry.swift`: actor-backed `bodyId → LineageEntry { graph, liveShape, root, fingerprint }`. As of #90/#91/#93 full completion, a body's `BRepGraph` is **retained across successive mutations** rather than rebuilt disposably per call: `currentInput(bodyId:path:)` re-stats the body's file and returns the cached `(shape, graph, root)` on a fingerprint match. No disk read: critical, since `add(_:absorbing:...)`'s absorb correlates by `TShape` object identity, and `Shape.loadBREP` mints a new `TShape` tree every call even for byte-identical content. It reloads fresh on any mismatch (first touch, or an out-of-band rewrite, e.g. `execute_script`). `commit(bodyId:path:output:ref:from:operationName:)` absorbs `ref` into the retained graph and returns `true` (continuation) when `historyRecordCount` actually grows, else falls back to a **generation reset**, a fresh graph built from `output` alone, and returns `false`. `absorb(into:root:output:ref:operationName:)` is the same primitive without a registry write, for the side of a shared-graph mutation whose own file is unchanged (boolean_op's b-side). `graph.add(...)`'s returned NodeRef is never trusted directly: `trackableRoot(for:in:)` re-resolves via `findNode(for:)` and drills a `.compound` result down to its wrapped `.solid` child, since `add(_:absorbing:...)` only tracks vertex/edge/face/solid nodes and boolean/`FeatureReconstructor` outputs register as `.compound` even for single-solid results. Since `BRepGraph` is a reference type, a graph shared across two `LineageEntry` keys (boolean_op's `outId` plus `aBodyId`; `apply_feature`'s output body plus its unchanged source body) mutates in place for both the instant `add()` runs, so no second registry write is needed for the side whose file didn't change. **Two-hop chaining:** chaining a SECOND `*WithFullHistory` op onto the *output* of a prior one (rather than a freshly-loaded shape) absorbs correctly. [SecondMouseAU/OCCTSwift#336](https://github.com/SecondMouseAU/OCCTSwift/issues/336) reported this as a "zero records absorbed" defect but was retracted in v1.15.2 as not a bug: the repro's second cut targeted a corner outside the box's actual bounds (`Shape.box` is centered at the origin, not corner-anchored), a genuine geometric no-op. See `HistoryRegistryLineageTests.swift` (in-process, asserts on `graph.instanceID`/`graph.contains(uid:)` directly, the rigorous check; its own hop 2 carried the identical box-centering mistake and is fixed the same way) and `IntegrationTests.swift`'s two-hop test (black-box; proves `remap_selection` stays correct end-to-end but can't distinguish genuine chaining from a lucky generation-reset fallback, since both report `confidenceMm: 0`).

- `Provenance.swift`: the `<output_dir>/provenance.json` sidecar, a top-level object keyed by body id recording how a derived body was made (`sourceBodyId` plus a `transform`). Populated only by `mirror_or_pattern`, so `find_correspondences` can default its `transformHint` when the caller omits one. A sibling of the scene manifest, never a substitute for it. `ProvenanceStore` takes the directory as an explicit parameter.
- **Sidecar write failures (#236).** A sidecar write is never `try?`. `annotations.json` and `zones.json` failures are `isError: true` results (`Failed to write annotations.json: ...`, `Failed to write zones.json: ...`); `ZoneRegistry.recordBatch`/`clear` and `ProvenanceStore.upsert`/`remove`/`clear` throw. `provenance.json` is best effort by design: `mirror_or_pattern`, `remove_body` and `clear_scene` have already changed the manifest, which is the source of truth, so they succeed and append `Warning: failed to ... provenance.json`. A zone registry whose write failed keeps the change in memory for the session.
- `Value+NumberValue.swift`: a back-port of `Value.numberValue` from modelcontextprotocol/swift-sdk#225, pending a tagged SDK release. JSON has one number type and `Value.init(from:)` tries `Int` first, so `Value.double(0)` round-trips to `.int(0)` and `doubleValue` returns `nil`; this accessor coerces both to `Double`, which is what tool-argument readers want.
